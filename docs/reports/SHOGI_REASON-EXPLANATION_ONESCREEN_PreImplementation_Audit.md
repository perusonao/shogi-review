## 3. 判定基準

集計の恣意性を避けるため、次の厳格な基準に固定した。

### 理由説明可能

実戦枝と推奨枝の差を、次のいずれかで比較できるもの。

- mateの有無または向きが両枝で異なる。
- 同じ最大6plyで、駒種別の増減が推奨枝で全項目非劣位かつ少なくとも1項目優位になる。任意の駒価ウェイトは使わない。
- 実戦枝の直後1〜2手にだけcheck/capture/mateがあり、かつ推奨枝側にもcheck継続、即時captureなどの客観的な利点がある。

### 部分説明可能

一方の枝のcheck、capture、promotion、drop、または短いPV上の事実は言えるが、「なぜ悪い」と「なぜ良い」の両方を比較で閉じられないもの。たとえば「推奨手は王手」「推奨手は桂打ち」は事実だが、それだけで優越理由とはしない。

### 評価差のみ

actual/best/lossはあるが、保存PVと盤面から差を説明する戦術事実を抽出できないもの。「水匠5は推奨手を高く評価」は表示できるが、Reasonブロックは生成しない。

### 説明不能

actual/best/score差さえ結び付かないもの。現行110件には該当なし。

## 5. 各理由候補の監査

### mate

採用可能。ただし「詰みを許した／逃した」は、両枝に型付きscoreがあり、片枝だけがmateである場合に限定する。CPの絶対値が大きいだけの旧データをmateへ自動変換しない。mate scoreだけなら「保存評価上」、盤面適用したPV終端が `is_checkmate` なら「保存PVでは詰みまで到達」と表現を分ける。

### 王手

合法手適用後の盤面から確実に判定できる。安全な文は「推奨手は王手です」「保存PVでは1手目と3手目に王手」。王手であることだけから「攻めが続く」「主導権を取る」は生成しない。「王手を続けられる」は、攻め手側の連続する各手番（1、3、5…）が王手の場合だけ許可する。

### 駒取り

移動先の駒から確実に判定できる。主語を必須にし、「推奨枝の3手目に自分が銀を取る」「実戦枝の2手目に相手が桂を取る」とする。現行文のように主語と枝を省いた「読み筋の2手目は桂を取る」は学習上も曖昧なので廃止候補。

### 成り・不成

USI末尾 `+` と合法手・盤面から判定可能。不成は「成れる合法局面で非成を選んだ」場合だけ表示する。成ったことから駒の働きや狙いを説明しない。

### 駒打ち

USIの `*` と持駒から判定可能。カードの「桂 / 7五へ打つ」表示に安全に使える。打った理由は、同時に王手・詰み・即時capture差などがなければ部分説明に留める。

### material swing

盤上と持駒を含む駒種別inventoryは安全に計算できる。ただし「飛=10、角=8」のような任意ウェイトで単一の駒得点を作ると、新たな評価モデルを導入することになる。実装は次に限定する。

- 同じply数まで到達できる両PVだけを比較する。
- 取得／喪失した駒を種類別に表示する。
- 推奨枝が全駒種で非劣位なら「保存手順内では推奨枝の方が少なくとも○○1枚分多く残る」と言える。
- 飛と複数小駒など異種交換は「交換内容」を列挙するだけで、駒得／駒損と断定しない。

このstrict条件で7件。

### immediate threat

実戦手後の次の1手、最大でも2手だけを見る。check/capture/mateのいずれかを盤面再生できた25件で候補化できる。「脅威」という抽象語だけにせず、「次に相手の○○が王手」「次に相手が○○を取る」と内容を明記する。

## 6. Reason構造案

常に3ブロックを埋めない。根拠があるブロックだけを表示し、空欄をもっともらしい一般論で補わない。

| 判定 | なぜ良くなかった？ | 推奨手の考え方 | 次に似た局面では |
|---|---|---|---|
| 理由説明可能 | 比較できるmate/check/capture/material事実 | 比較できる対案の事実 | 同じ検査手順をチェックリスト化できる場合だけ |
| 部分説明可能 | 保存評価差、または実戦枝の事実だけ | 推奨手の客観的特徴だけ | 原則非表示。直後1〜2手の王手・取り・詰みがある場合だけ表示可 |
| 評価差のみ | 「保存評価では低下」まで | 「水匠5推奨」まで | 非表示 |
| 説明不能 | ブロック自体を表示しない | 表示しない | 表示しない |

安全な生成順序は `mate差 → 即詰み → 王手差/継続 → 直後1〜2手のcheck/capture → strict material差 → 成り/不成 → 打ち → 評価差のみ`。先に強い根拠が採れたら、弱い一般論を追加しない。

「次に似た局面では」は棋理の結論ではなく、今回実際に検出したイベントを再確認する操作へ落とす。

- mate差あり: 「指す前に、相手の王手を2手先まで確認します。」
- 推奨側の連続王手あり: 「候補手ごとに、王手が次の自分の手番にも続くか確認します。」
- immediate captureあり: 「指した直後、相手に取られる駒がないか確認します。」
- 根拠がpromotion/dropだけ: 一般化を生成しない。

## 7. ryunenbb vs sonao81 80手目

### 保存データ

| 項目 | 実戦 | 推奨 |
|---|---|---|
| 手 | △5二金 (`6b5b`) | △7五桂打 (`N*7e`) |
| 保存score | `mate -5` | `cp -7578` |
| 初手王手 | なし | なし |
| 初手駒取り | 銀を取る | なし（桂打ち） |

実戦PV:

`△5二金 → ▲6六角 → △7五桂打 → ▲同角 → △8四香打 → ▲8二龍`

- ▲6六角は王手。
- ▲同角は桂を取りながら王手。
- ▲8二龍は王手で、保存盤面へ適用すると詰み。
- よって「実戦手のあと、保存された読み筋では相手の王手が続き、▲8二龍で詰みです」は安全。

推奨PV:

`△7五桂打 → ▲同歩 → △6九龍 → ▲同玉 → △5二金 → ▲同角成 → △4七歩成 → ▲8二龍 → △8四玉`

- △7五桂打は王手ではない。
- ▲同歩に桂を取られる。
- △6九龍が王手。その後▲同玉に龍を取られる。
- 5手目の△5二金は銀を取るが、次に▲同角成で金を取られる。
- 保存scoreはmateではなく `cp -7578`。依然として大差で不利だが、実戦枝の `mate -5` とは異なる。

### 生成可能な3ブロック

【なぜ良くなかった？】

> △5二金のあと、保存された読み筋では▲6六角、▲同角、▲8二龍と相手の王手が続き、▲8二龍で詰みです。保存評価も「相手に5手の詰み」です。

【推奨手の考え方】

> 水匠5の推奨は△7五桂打です。保存された推奨手順では初手は王手ではありませんが、評価は「相手に5手の詰み」ではなく `-7578` です。詰み評価を外す手として比較できます。

UIでは `-7578` を「相手優勢」と併記し、「助かる」「互角に戻る」と誤解させない。

【次に似た局面では】

> 指す前に、相手の次の王手と、その次の自分の応手後も王手が続くか確認します。

この一般化は実戦PVの2、4、6手目の連続王手を根拠にした確認手順であり、「金を動かしたことが原因」という棋理解釈ではない。

### 禁止する説明

- 「△5二金で守りが薄くなった／玉形が悪くなった」
- 「金を動かしたから詰んだ」
- 「△7五桂打が攻めを速くする／主導権を握る」
- 「△7五桂打で王手を続けられる」—初手は王手でなく、攻め手側の連続王手にもなっていない。
- 「桂を捨てて龍を切るのが唯一の受け」—保存PVは一変化であり唯一性を証明しない。
- 「△7五桂打なら詰みを完全に回避できる」—保存された有限探索のscore差としては言えるが、数学的な非詰み証明ではない。「保存評価では詰み表示がない」と表現する。

## 8. One-Screen UX監査

公開版をブラウザviewport 390×844で実測した。下部ナビ58pxを除き、`.app` は786px、`#reviewView` の実表示高は780px。

### 80手目の実測

| 領域 | 高さ |
|---|---:|
| 対局情報top | 25px |
| 盤＋上下持駒 | 429px |
| 前後操作 | 28px |
| 評価 | 58px |
| この一局のポイント・閉 | 25px |
| 現在の課題カード（PV閉） | 169px |
| 次局への学び・閉 | 25px |
| 次の課題局面へ | 27px |
| reviewViewのmargin等込みcontent高 | 810px |
| reviewView表示高 | 780px |
| 超過 | 30px |

展開状態では、「この一局のポイント」だけ展開で930px（150px超過）、両方展開で1019px（239px超過）。現行コードは新しい対局を開くと両方を展開状態へ初期化するため、初期表示が最も長い。

### 主原因

単独の原因ではなく、429pxの盤領域の下へ、58px評価、最大169pxの課題、独立27pxの次課題ボタン、2本の25px disclosureが直列に積まれること。盤は主要操作なので、最初に削る対象ではない。

### 推奨情報設計

常時表示:

- 対局情報
- 盤面と持駒
- 前後操作（ここへ「前/次の課題」を小ボタンで統合）
- 評価
- 現在の課題: 実戦/推奨カード、評価差、最も強いReason 1件

初期折りたたみ:

1. 次局への学び
2. この一局のポイント（課題局面表示中。開始局面では展開してよい）
3. 詳細PV
4. Reasonの第2候補以降

独立した「⚠ 次の課題局面へ」27pxは廃止し、前後操作を `◀ | 手数 | ▶ | 次課題 ⚠` の4列、または課題見出し右端の28pxアイコンへ統合する。これだけで約30pxを回収し、現行カード高のままでも閉状態を780px内へ収められる見込み。

Reason Explanationでカードが伸びるため、3ブロックは長文3段ではなく、各1行の見出し＋最大2行本文とする。最上位Reasonだけ常時表示し、「理由を詳しく」で残りを展開する。目標は課題領域150〜165px、閉状態content高765〜780px。

## 10. 色監査

現行盤色 `#d7a253` に対する現行markerのコントラストは、赤 `#ff4938` が1.47:1、緑 `#38d86a` が1.22:1。どちらも非テキストUIの目安3:1を満たさず、特に緑が盤へ溶ける。

赤=実戦、青=推奨を採用する。ただし盤上と暗色カード上で同じ明度を使い回さず、同一hueのsurface別tokenにする。

| 用途 | 実戦 | 推奨 | 対背景contrast |
|---|---|---|---|
| 盤marker/arrow | `#A11222` | `#0047AB` | 盤色に3.50:1 / 3.69:1 |
| 暗色カードborder/text | `#FF6B5A` | `#5DA9FF` | `#1c1711` に6.36:1 / 7.27:1 |

意味色を次へ一括適用する。

- 盤面arrow、移動先枠、drop marker
- カードborderと「実戦／推奨」label
- 凡例
- PVの枝見出しと手順先頭marker
- 評価比較内のactual/best indicator

色だけに依存しないため、盤上の `実` / `推`、カードlabel、PVの「実戦手なら／推奨手なら」を残す。さらに実戦は実線、推奨は破線または二重枠などshape差を付けると、重なりと色覚多様性に強い。

## 11. 実装ガードレール

1. Reason生成器は保存JSONと盤面再生結果だけを入力にする。
2. 各文へ内部的に `evidenceType`, `branch`, `pvPly`, `moveUsi`, `piece`, `score` を紐付け、根拠なしの文を出せない型にする。
3. actual/recommendedを必ず別々に再生する。推奨PVのcaptureを実戦手の結果として表示しない。
4. PVの一変化から「唯一」「必然」「狙い」「原因」を生成しない。
5. 駒価ウェイトによるmaterial断定を追加しない。
6. 3ブロックの強制充足をしない。根拠がなければブロックを省略する。
7. B-strictの選択、cluster、learning最大件数、thresholdはReason生成器から参照するだけで変更しない。
8. 390×844回帰は、開始局面、通常局面、課題局面、PV展開、最大3件learningの5状態で `scrollHeight/clientHeight` を検査する。

## 12. 次の実装Phase
